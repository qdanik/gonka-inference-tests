# kimi-specific — JSON Schema `$ref` probes

This set reproduces the upstream report *"Kimi-K2.6 OpenAI-Compatible Tool
Schema Rejects `$ref`"* (`kimi-k26-tool-ref-upstream-report.md`). Each spec is a
normal inference spec — `{messages, max_tokens, seed, tools|response_format}` —
whose tool / structured-output schema embeds a JSON Schema `$ref` in a
different shape. They run through the standard flow (`e2e infer`), which sends
`tools` / `response_format` to the server verbatim.

The report's failure (`schema reference keyword is forbidden: "$ref" is not
allowed`, HTTP 400) is raised by the **Gonka gateway** that fronts the
executor. `e2e infer` tunnels straight to vLLM, so these probes answer a
different, complementary question: **does vLLM itself accept each `$ref` shape?**
Combined with the gateway's own behaviour (reproduce that with the `curl` in the
report), they localize exactly where each shape is rejected.

## Probes

| label | `$ref` shape | why it's here |
|---|---|---|
| `tool_ref_defs_en` | `#/$defs/Path` in a tool param | exact minimal reproducer from the report |
| `tool_ref_definitions_en` | `#/definitions/Path` | older Draft-07 keyword — does the validator treat it the same? |
| `tool_ref_array_items_en` | `$ref` inside array `items` | `$ref` not at the top level of the property |
| `tool_ref_anyof_en` | `$ref` inside `anyOf` | optional-via-ref pattern; `$ref` under a combinator |
| `tool_ref_recursive_en` | self-referencing `Node` | report flags recursion as un-inlineable — a dereferencer must detect the cycle |
| `tool_ref_multi_late_en` | 12 tools, `$ref` only in the **last** | mirrors `tools[287]`: the validator must walk the whole tool list |
| `rf_ref_defs_en` | `$ref` in `response_format.json_schema.schema` | structured-output path, not tools |
| `tool_noref_inlined_en` | **none** (fully inlined) | CONTROL — must be accepted; isolates `$ref` as the sole cause of any rejection |

## How to run

```bash
# Whole set against a Kimi-K2.6 box (see docs/kimi.md for the deploy recipe):
python3 -m e2e infer \
  --ssh-host shadeform@<ip> --gpu-name <tag> \
  --model-name moonshotai/Kimi-K2.6 \
  --logprobs-mode raw_logprobs \
  --inferences-dir inferences/kimi-specific

# A single probe:
python3 -m e2e infer ... \
  --inferences-dir inferences/kimi-specific \
  --inferences tool_ref_defs_en
```

## How to read results

Each probe writes `artifacts/<date>/Kimi-K2.6-<tag>/<label>/inference-N.json`.

- **`error` set, no completion** → the server rejected the schema before
  inference. For the `$ref` probes that's the report's behaviour reaching vLLM.
  The `error` string carries vLLM's reason (a `requests` `HTTPError`); for the
  exact gateway wording, also run the report's `curl` against the proxy.
- **`tool_noref_inlined_en` must succeed** (a normal completion / tool call). If
  it fails too, the problem is *not* `$ref` — re-check the deploy
  (`--enable-auto-tool-choice --tool-call-parser kimi_k2`).
- Compare which `$ref` shapes fail vs. which pass to see whether the rejection
  is blanket (`$ref` anywhere) or shape-specific (e.g. only `#/$defs`).

> These are hand-maintained (they encode exact schemas from an external
> report), unlike `inferences/default/` which is generated by
> `scripts/generate_inferences.py`.
